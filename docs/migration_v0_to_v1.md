# 移行ガイド

v0（v0.19.x 以前の `deploy.sh` で作った環境）のデータを、v1.x 系の環境へ移す手順です。v1.x 系は v0 と後方互換がありません。v0 はそのまま動かしておき、同じアカウントに v1 をデプロイしてから、移行スクリプト `scripts/migrate_v0_to_v1.py` で v0 のデータを v1 へコピーします。

- v0 のデータは読むだけで、書き換えも削除もしません。移行のあとも v0 はそのまま使えるため、問題があれば v0 に戻せます
- スクリプトは既定で dry-run（何も書き込まない）です。書き込むのは `--apply` を付けたときだけです
- 何度実行しても同じ結果になります。v1 にすでにあるデータは「移行済み」として扱い、上書きしません。途中で止まったら、そのまま実行し直します

## 移行できるもの・できないもの

| データ | 移行 | v1 での扱い |
|---|---|---|
| 利用者（Cognito） | ○ | v1 のユーザープールに作り直します（下の「[利用者と所有者](#利用者と所有者)」） |
| ペルソナ（アバター画像を含む） | ○ | 所有者を付けます（下の「[利用者と所有者](#利用者と所有者)」） |
| 議論・インタビューの結果（発言、レポート、添付資料を含む） | ○ | 同上 |
| アンケートテンプレート（画像を含む） | ○ | 同上 |
| アンケート（結果の CSV を含む） | ○ | 同上。実行中・待機中だったアンケートは「エラー（中断）」になります |
| データセット | ○ | 利用範囲は対応表で決めます。未指定なら admin だけが使えます |
| ナレッジベースの登録 | ○ | 同上。v1 と v0 のリージョンが違うときは、ナレッジベースを v1 のリージョンに作り直してください（下の「[注意](#注意)」） |
| カスタムペルソナデータ | ○ | 同上 |
| ペルソナとデータセット・ナレッジベースの紐付け | ○ | 両方が v1 にあるときだけ移ります |
| Nemotron のペルソナデータ | × | v1 で取得し直します（下の「[手順 3](#3-v1-をデプロイし最初の-admin-を作る)」） |
| ペルソナの長期記憶（AgentCore Memory） | × | v1 では空から始まります |
| パスワード | × | 書き出せないため、利用者は v1 で設定し直します |
| ジョブ、ログインのセッション、一時ファイル | × | 一時的なデータのため移しません |
| 議論の添付やテンプレートに付いていないアップロードファイル | × | v1 では使われないため移しません |

## 利用者と所有者

- **利用者:** v0 のユーザープールの利用者を、メールアドレスで v1 のユーザープールに作り直し、`role:member` に入れます。v1 に同じメールアドレスの利用者（最初に作った admin など）がいれば、作り直さず、ロールやグループも変えません。大文字と小文字、前後の空白の違いは同じとみなします。メールアドレスのない利用者、ほかと重なる利用者、v0 で無効にした利用者は作りません
- **所有者:** v0 のデータには作成者の記録がありません。移したデータは、既定の所有者（`--default-owner` に指定した v1 の admin）のものになります。グループへの共有は、移行のあとに admin が画面から設定できます。所有者を変えたいリソースがあるときだけ、任意の対応表で指定します（[手順 4](#4-オプション対応表を用意する)）

## 前提

- v0 と v1 が同じ AWS アカウントにあること。v0 の既定のリージョンは `us-east-1`、v1 は `ap-northeast-1` です。別のリージョンでも、オプションで指定できます
- v0 と v1 が並行して動くため、その間は両方の料金がかかります。VPC と Elastic IP のクォータ（既定は各 5 / リージョン）に空きがあることを確かめてください
- 実行には、v0 と v1 の両方を扱える管理者の認証情報が必要です（v0 の DynamoDB の Scan、S3 の読み取り、両方の Cognito、CloudFormation と ECS の参照、v1 の DynamoDB と S3 への書き込み）

> **重要:** v0 の dev 環境（`--env prod` 以外）は、スタックを削除するとテーブルとバケットのデータも消える設定です。移行と確認が終わるまで、`scripts/destroy-v0.sh` を実行しないでください。

## 手順

### 1. v0 をバックアップする

v0 の各テーブルのオンデマンドバックアップを取ります（v0 の PITR は有効ですが、念のため移行の前の時点を残します）。

```bash
SOURCE_REGION=us-east-1
for table in $(aws dynamodb list-tables --region "$SOURCE_REGION" \
    --query "TableNames[?starts_with(@, 'AIPersonaDev_')]" --output text); do
  aws dynamodb create-backup --region "$SOURCE_REGION" \
    --table-name "$table" --backup-name "${table}-before-v1"
done
```

`AIPersonaDev_` は v0 のテーブル名の先頭です（`--env prod` でデプロイした環境は `AIPersona_`）。S3 のバケット（`aipersonadev-uploads-<アカウント>-<リージョン>`）はバージョニングが有効なことを確かめます。

```bash
aws s3api get-bucket-versioning --bucket <v0 のバケット名>
```

### 2. スクリプトを動かす準備をする

CloudShell（v1 のリージョン）で、リポジトリを取得します。CloudShell のホームは 1 GB までのため、Python の環境とキャッシュは `/tmp` に置きます。`/tmp` は CloudShell を閉じると消えるため、開き直したらこの手順をやり直します。

```bash
git clone https://github.com/aws-samples/sample-ai-persona.git
cd sample-ai-persona
curl -LsSf https://astral.sh/uv/install.sh | sh
source ~/.local/bin/env
export UV_CACHE_DIR=/tmp/uv-cache UV_PROJECT_ENVIRONMENT=/tmp/ai-persona-venv
uv sync --no-dev
```

手元の PC で実行するときは、`uv sync` のあと AWS CLI と同じ認証情報（管理者）を使えるようにしておきます。

### 3. v1 をデプロイし、最初の admin を作る

[CDK デプロイガイド](../cdk/README.md) のとおりに v1 をデプロイし、「[デプロイ後: 最初の admin を作る](../cdk/README.md#デプロイ後-最初の-admin-を作る)」で admin を 1 人作ります。この admin を、移行するデータの既定の所有者にします。

v0 で使っていたメールアドレスで admin を作っても構いません。v1 にすでにいる利用者は、移行で作り直したりロールを変えたりしません。

Nemotron のペルソナデータは移しません。マスアンケートで使う場合は、v1 で取得し直します。公開構成では admin が画面の「ペルソナデータの準備」からダウンロードします（[ユーザーガイド](user_guide.md)）。閉域構成では [閉域構成ガイドの「Nemotron のデータを置く」](closed_network.md#nemotron-のデータを置く) の手順で置きます。

### 4. （オプション）対応表を用意する

v0 のデータには作成者の記録がありません。対応表を使わなければ、移したデータはすべて既定の所有者（手順 3 の admin）のものになり、共有はされません。そのあと admin が画面から、ペルソナや議論などをグループへ共有し（「自分のもの」タブで複数を選んで「共有先を設定」）、データセット・ナレッジベース・カスタムペルソナデータの利用範囲を設定できます（[ユーザーガイド](user_guide.md)の「共有と権限」「組織資産の利用範囲」）。多くの場合は、対応表なしで移して画面から共有すれば足ります。

対応表（CSV、`--mapping` で渡す）は、次のときにだけ作ります。対応表に書くのは、既定と違う扱いにしたいリソースだけです。書かなかったリソースは既定の admin のもので、共有なしで移ります。

- **所有者を変えたいリソースがある:** v1 には所有者を変える画面がありません。admin 以外の人に編集・削除・共有をさせたいもの、member との会話を長期記憶にためたいペルソナ（共有されたペルソナは所有者以外との会話を記憶に書き込みません）は、対応表で所有者を指定します
- **移行と同時に共有・利用範囲を設定したい**
- **移したくないリソースがある**

所有者だけを変えるなら、必要な列は 3 つです（`group_ids` と `action` の列は省けます）。

```csv
resource_type,resource_id,owner_email
persona,0a1b2c3d-...,sato@example.com
discussion,4e5f6a7b-...,suzuki@example.com
```

共有先の指定や除外もするときは、列を足します。

```csv
resource_type,resource_id,owner_email,group_ids,action
persona,0a1b2c3d-...,sato@example.com,sales;planning,
discussion,4e5f6a7b-...,,sales,
survey,8c9d0e1f-...,,,skip
dataset,2a3b4c5d-...,,sales,
custom_persona_data,営業部の顧客,,sales,
```

| 列 | 内容 |
|---|---|
| `resource_type`（必須） | `persona`、`discussion`（インタビューを含む）、`survey_template`、`survey`、`dataset`、`knowledge_base`、`custom_persona_data` |
| `resource_id`（必須） | v0 の ID。カスタムペルソナデータだけは v0 での名前 |
| `owner_email` | 所有者のメールアドレス。空なら既定の所有者。v1 にいる利用者か、同じ実行の `users` で作り直す利用者に限ります。データセット・ナレッジベース・カスタムペルソナデータには書けません（所有者を持たない組織の資産のため） |
| `group_ids` | 共有先（データセット等は利用範囲）のグループ。`;` で区切ります。`group:` は付けても付けなくても構いません |
| `action` | `migrate`（既定）か `skip`。`skip` の行は移しません |

- ID は v0 の画面の URL（`/persona/<ID>` など）か、DynamoDB のコンソールで確かめます
- 対応表で使うグループは、先に v1 のユーザープールに作っておきます（[利用者・ロール・グループの管理の「グループを作る」](user_management.md#グループを作る)）。v1 にないグループや、v1 にいない所有者を書くと、スクリプトは何も書き込まずに止まります
- **所有者が決まるのは、v1 に初めて書くときだけです。** 一度移したリソースは、対応表を直して実行し直しても所有者は変わりません。対応表は最初の `--apply` の前に用意してください。dry-run で「作成予定」に入っているうちは間に合います

### 5. dry-run で確かめる

```bash
uv run python scripts/migrate_v0_to_v1.py --default-owner <手順 3 の admin のメールアドレス> \
  [--mapping mapping.csv]
```

最初に v0 と v1 のリソース（リージョン、バケット、ユーザープール）が表示されます。正しい環境を指していることを確かめてください。最後に、種別ごとに次の件数が表示されます。

| 表示 | 意味 |
|---|---|
| v0 | v0 にあった件数 |
| 作成予定 / 作成 | v1 に作る（作った）件数 |
| 移行済み | v1 にすでにあるため、そのままにした件数 |
| 共有の設定 | グループへの共有・利用範囲を設定する（した）件数 |
| スキップ | 移さなかった件数と理由（下の表） |
| 失敗 | 移せなかった件数。理由が下に表示されます |

| スキップの理由 | 意味 |
|---|---|
| `mapping_skip` | 対応表で `skip` にした |
| `persona_missing` / `target_missing` | 紐付けの相手（ペルソナ、データセット、ナレッジベース）が v1 にない |
| `not_in_s3` | データセットのファイルが S3 にない（ローカルで動かしていた環境のデータ） |
| `name_taken` | v1 に同じ名前の別のカスタムペルソナデータがある |
| `name_invalid` | カスタムペルソナデータの名前が空か 100 文字を超える |
| `email_missing` / `email_invalid` / `email_duplicate` | v0 の利用者のメールアドレスがない、形が正しくない、ほかの利用者と同じ |
| `disabled` | v0 で無効にした利用者 |

#### 移す種別を選ぶ

`--include` で移す種別を、`--exclude` で移さない種別を、カンマ区切りで指定します。既定はすべてです。

```bash
# 利用者とペルソナだけ
uv run python scripts/migrate_v0_to_v1.py --default-owner <admin> --include users,personas
# 議論とアンケートを除く
uv run python scripts/migrate_v0_to_v1.py --default-owner <admin> --exclude discussions,surveys
```

| 種別 | 内容 |
|---|---|
| `users` | 利用者 |
| `datasets` | データセット |
| `knowledge_bases` | ナレッジベースの登録 |
| `custom_persona_data` | カスタムペルソナデータ |
| `personas` | ペルソナ（アバター画像を含む） |
| `bindings` | ペルソナとデータセット・ナレッジベースの紐付け |
| `survey_templates` | アンケートテンプレート（画像を含む） |
| `surveys` | アンケート（結果の CSV を含む） |
| `discussions` | 議論・インタビューの結果（発言、レポート、添付資料を含む） |

- 画像・添付資料・発言などは、それを持つリソースと一緒に移ります
- 紐付けは、ペルソナと相手の両方が v1 にあるときだけ移ります。ペルソナを除くと、紐付けは `persona_missing` でスキップされます
- カスタムペルソナデータを除くと、それを使ったアンケートはデータの名前だけを残して移ります（結果は見られます）
- 議論の参加者のペルソナを除いても、議論は移ります（参加者の名前は議論に残っています）
- 何回かに分けて実行しても構いません。紐付けは、あとからペルソナや相手を移してから実行し直せば移ります。アンケートだけは、先に移したときのカスタムペルソナデータの参照が直らないため、カスタムペルソナデータを先に（または一緒に）移してください

#### その他のオプション

| オプション | 説明 |
|---|---|
| `--source-env <名前>` | v0 の `deploy.sh --env` の値（既定: `dev`） |
| `--source-region <リージョン>` | v0 のリージョン（既定: `us-east-1`） |
| `--target-region <リージョン>` | v1 のリージョン（既定: `ap-northeast-1`） |
| `--closed` | v1 が閉域構成のとき（Stage `AIPersonaDevClosed`。利用者は招待メールを送らずに作ります） |
| `--target-stage <名前>` | v1 の Stage 名を直接指定するとき |

### 6. 本実行する

移行の間に v0 で作ったり変えたりしたデータは、v1 に反映されないことがあります（v1 にすでにあるデータは上書きしないため）。利用者に v0 の利用を止めてもらってから実行します。

```bash
uv run python scripts/migrate_v0_to_v1.py --default-owner <admin> [--mapping mapping.csv] --apply
```

失敗が 1 件でもあると、終了コード 1 で終わります。表示された理由を直して、同じコマンドを実行し直します。v0 のファイルがなくなっていて失敗するリソース（`... がありません`）は、v0 側を直すか、対応表で `skip` にします。

共有の索引が本体と合っていることは、次のコマンド（変更しない）で確かめられます。「ずれはありません」と出れば合っています。`*_TABLE_NAME` の値は v1 の ECS タスク定義の環境変数にあります。

```bash
RESOURCE_SHARES_TABLE_NAME=... PERSONAS_TABLE_NAME=... DISCUSSIONS_TABLE_NAME=... \
SURVEY_TEMPLATES_TABLE_NAME=... SURVEYS_TABLE_NAME=... \
  uv run python scripts/rebuild_resource_shares.py --region ap-northeast-1
```

### 7. 確かめる

代表的な利用者で v1 にログインし、次を確かめます。

- admin: すべてのデータが「すべて」タブに出る。ペルソナのアバター、議論の発言・レポート・添付資料、アンケートの結果とテンプレートの画像が開ける
- グループに入った member: 自分が所有者のデータと、グループに共有されたデータが見える
- グループに入っていない member: 自分が所有者のデータだけが見える

### 8. 利用者に案内する

- v1 の URL（`deploy.sh` の最後に表示される `AppUrl`）を案内します
- 公開構成では、作り直した利用者に v1 から仮のパスワードがメールで届きます。最初のログインで新しいパスワードを設定してもらいます
- 閉域構成（`--closed`）では招待メールを送りません。利用者ごとに、[閉域構成ガイドの「パスワードを忘れたとき」](closed_network.md#パスワードを忘れたとき) のコマンドで一時パスワードを設定し、別の経路で伝えます
- 作り直した利用者は全員 `role:member` です。admin にする利用者は、[ロールを付ける](user_management.md#ロールを付ける) の手順で `role:admin` に入れてから `role:member` から外します
- 利用者を部署などのグループに入れます（[利用者・ロール・グループの管理](user_management.md)）

### 9. v0 を片付ける

問題があれば、利用者に v0 の URL を案内し直せば v0 に戻れます（v0 のデータは移行前のままです）。

v1 で問題がないことを確かめたら、利用者の判断で v0 を削除します（[CDK デプロイガイドの「v0 の環境を削除する」](../cdk/README.md#v0-の環境を削除する)）。v0 を削除すると、v0 には戻れなくなります。手順 1 のバックアップは、DynamoDB のバックアップの一覧から不要になったときに削除します。

## 注意

- **ナレッジベース:** Bedrock のナレッジベースはリージョンごとの資源です。v0 と v1 のリージョンが違うと、v1 から v0 のナレッジベースを使えません。v1 のリージョンにナレッジベースを作り直し、画面の登録を新しい ID に直してください。スクリプトは、この場合に注意を表示します
- **長期記憶:** ペルソナの長期記憶（AgentCore Memory）は移りません。v1 では、新しい会話から記憶をためていきます
- **所有者:** 対応表に載らないデータは既定の所有者のものになり、その人と admin だけが見られます。リリースの前に、利用者へ周知してください
- **アンケート:** v0 で実行中・待機中だったアンケートは再開できないため、「エラー（中断）」として移ります
